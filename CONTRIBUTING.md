# Contributing to Kelus

Thank you for improving source-backed study.

## Before you start

1. Open an issue for a substantial feature or a change to the learning model.
2. Never add private notes, student data, API keys, or unlicensed teaching
   material to an issue, fixture, screenshot, or pull request.
3. Keep a question traceable to a real line in the source. If Kelus cannot
   verify it, it must say so instead of guessing.

## Pull requests

- Keep each pull request focused.
- Preserve the source-first workflow: material → topic → answer → evidence →
  next step.
- Add or update tests when changing extraction, question generation, answer
  checking, scheduling, imports, or deletion.
- Run the checks listed in the README before requesting review.
- Describe the student-facing effect, not only the implementation.

## Design principles

Kelus should feel calm, direct, and useful on a phone. Do not add visual
chrome, generic dashboards, looping decoration, or AI claims that the product
cannot prove. The student's original material is the source of truth.
